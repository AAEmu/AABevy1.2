Read-only S/M roadmap projection audit ? 2026-10-23

Result
======
Concrete aa-client producer defect proven. Image-normalized position is NOT
generally size-invariant. Both ingame.lua's player conversion and markers.lua's
ordinary NPC/quest conversion use base926x556 and the _100 frame even while
original Lua selects _50/_70 art. aa-ui then correctly applies those image UVs
to the selected art's actual offset/extent, yielding a different Map-relative
centre than native1.2. City maps have the same problem; it is not zone-only.
No aa-ui API/renderer change is needed to correct this centre-projection defect.
No production/source/docs edits, Cargo, builds, GPU/client/server/process work,
subagents, or new API were used. Only this ignored research directory was written.
Default large, type5 persistence and bottom532/516 sampling remain separate.

Equations and original size forms
================================
Let selected world rectangle be (X,Y,W,H), game Y up:
  uw=(x-X)/W
  vw=1-(y-Y)/H
Native centre relative to current Map:
  px=uw*MapWidth
  py=vw*MapHeight
Original Resize indices1/2/3 choose rates0.5/f32(0.7)/1.0, window/Map dimensions:
  S:463 x278; M:648.2000122070312 x389.1999816894531; L:926 x556.

Original registered selected-size art is offset(Ox,Oy), extent(Cw,Ch).
The EXISTING aa-ui image-normalized hook contract therefore requires:
  image_u=(px-Ox)/Cw
  image_v=(py-Oy)/Ch
Then current aa-ui placement gives Map-relative centre:
  Ox+image_u*Cw, Oy+image_v*Ch, before its existing per-drawable rounding.
This inverse is derived from executed native projection plus original Lua
art anchors; it is not a guessed divide-by-size correction.

  M(70): offset36,4; extent540,360.
  L(100): offset43,6; extent780,532.
Original city335 forms:

City144: S145,0 /220,220; M205,0 /304,304; L292,0 /436,436.

Current error, derived and executed against unchanged producer Lua
==================================================================
Current player helper and ordinary-marker helper both compute:
  u100=(uw*926-Ox100)/Cw100; v100=(vw*556-Oy100)/Ch100.
Their selected-size centre becomes Ox_s+u100*Cw_s, Oy_s+v100*Ch_s.
It equals native for every point only if offset AND extent scale exactly with
Map size on both axes. That identity fails for the listed original forms.
The world->Map normalized uw/vw ARE size invariant; image_u/image_v are not.
Simply returning uw/vw to today's aa-ui hook would also be wrong because aa-ui
expects image UV, not widget UV. No hook meaning should be silently changed.

Original UpdateRoadmapAnchor places the containing window so the selected art
ends at the right margin. This moves native and current positions by the SAME
window origin; it cannot cancel the relative-centre error above. UI scale later
maps these UI-unit errors to pixels. A native pixel/visual oracle was not run.

Cache requirement
=================
Current markers.lua road.key includes icon version, filter version, level,zone,
zone_group, but no selected size/frame or current Map extent. Executing its
unchanged closure with icon version fixed while widths change926->463->648.2->926
retains the same markers_version and same image UV list. Once projection becomes
size-aware, selected size/frame and relevant dimensions must invalidate that
cache/version. aa-ui already re-places its pool when shown_map changes; that
cannot repair stale producer UVs. Player is read every frame and also remains
unchanged in the present fixed100 producer control.

Smallest owning-crate correction proposal, no implementation here
================================================================
aa-client only, root-owned:
1. Keep today's image-normalized AAUI.RoadMap player/marker contract and aa-ui
   renderer. Read the CURRENT roadmap:GetExtent() using its existing widget API.
   Identify the active50/70/100 frame from the original live Resize extent pair;
   e.g. round(MapWidth*100/926) inverts the proven Resize equation, accepting only
   the original three matching pairs. Do not use persisted X2 getter.size as
   live geometry: original SetValue can clamp invalid values, and state writes
   can be deferred or absent when a checkbox does not change.
2. Provide the actual selected-size plain-number zone/city frames in the existing
   hud/road_frames.lua data; today it only contains _100. Locale-controlled
   frames should continue coming from original FORM_ROAD_MAP_LIST with suffix
   _50/_70/_100. The executed282-form JSON is evidence for generating the data,
   not a proposed hardcoded English-only replacement of original locale forms.
3. Update both existing onRoadImage conversions (hud/ingame.lua and markers.lua)
   to use current Map width/height and that frame's offset/extent in the inverse
   equation above. Keep city selection/own sub_map_rect and zone selection/
   zone_rect as they are for this projection correction.
4. Add selected frame/size and relevant dimensions to roadMarkers cache key,
   causing markers_version to advance when UVs change even if contacts do not.
No new native/game API, aa-ui patch, crop/opacity change or type5 change is
required for those centre corrections. Avoid a single fixed offset or globally
rescaling marker artwork; native projection anchors centres independently.

Important admission boundary: current roadMarkers also filters with
inside(image_u,image_v). That is a producer art-box admission heuristic, while
native392aed20 has descriptor/category/NPC flags, zone/city/exploration rules.
This oracle controls native visibility true and measures centre projection.
Changing normalized UVs can alter that heuristic's edge decisions. Keep the
centre fix and icon admission decision explicit; require a native visibility
control before changing which edge/outside-art markers are admitted. The centre
examples above are inside all relevant art boxes. No removal of filters or new
visibility/clip policy is justified by this numeric audit alone.
