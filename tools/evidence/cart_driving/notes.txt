S6/S7 live drive of the original 1.2 client (r208022), hidden, single launch (pid 46236), login 127.0.0.1:31237 (slave-occupy lane), new account <account>, character Driver, GM level 100. Cart = slave template 60 (Farm Wagon, model 1008), client unit id 0x84C9 (the id its packets and interactions use), slave timeline 79.
Samples: the cart is read every ~100 ms from the client's own engine through the driver (client_entities, class prefab_unit, name Farm Wagon: world position, Euler angles, velocity, terrain height; the cart's unit object has no entity reachable at unit+0x3be8 -> model+0x1f0 -> +0xc on this build, so the read is the engine entity, not that pointer chain). The driver's position/quaternion is read from its unit each sample. Every 5th sample adds the vehicle block (client_vehicle: mounted/driver/speed/turn_speed). The read costs 9-57 ms (row 'cart_read_ms'), and the achieved cadence is in the sample timestamps.
Input is the client's own key path through aaemu-clientdriver client_input (CryInput on the client main thread, no OS input): w/s for forward/reverse and a/d for the steering, as the client's own key path; no desktop mouse or keyboard events.
The lane's log prints only the C->S field trace (aaemu_game::net::fields=trace) plus the StartInteraction warn line; it has no S->C packet lines (aaemu_game::net=debug is off), and the lane must not be restarted, so S->C movement/attach packets are NOT CAPTURED - the client-side effect (mounted/driver/vehicle info) is recorded instead.
Provenance of this file: the drive cases a-f are from the second capture run on the same client (03:22-03:23). The first run (03:12-03:13) wrote its files into s67/, then the screenshot retake slices (which shared that output directory) overwrote native.json; the cases were therefore recorded again, unchanged in procedure, and this file holds the second (complete) run. No client was restarted: every run above is a new MCP attachment to the same pid.
Screenshots: attempt 1 (inside the a-f run) failed - UIParent:SetViewCameraPos / SetViewCameraAngles / SetViewCameraFov return true but leave the camera object (x2game+0xb0e2b8: mode/pos/fov) unchanged, so the free camera stayed at the player's head and the images showed empty ground (those rows were in the first run's file, which the retake slices overwrote, so they are not in this file). Attempt 2 (case g2) used the follow camera through the client's own console setters and framed the cart, but bushes blocked the behind view; those shot rows are dropped (8 rows) and their images were replaced. Attempt 3 (case g3) is the delivered set: same console setters, camera measured before each shot, on the open field.
g3 camera: side = yaw offset 90 deg, behind = 0, front = 180 through the client's own console setters uc_set_yaw/uc_set_pitch/uc_set_wheel_dist; positions measured from the camera object (x2game+0xb0e2b8 +0x64).
Camera control that works on this build: System.ExecuteCommand('uc_set_yaw <deg>'), 'uc_set_pitch <deg>', 'uc_set_wheel_dist <m>' in the client's system Lua state; the camera object is the follow camera (x2game+0xb0e2b8, mode 1, place +0x64, yaw +0x80 heading and +0x84 offset, arm +0x38, fov +0x98 in radians). uc_set_yaw takes degrees.
Coordinates: the client streams with a seamless origin, so its local position is the server position minus (7168, 11264) here. The CSMoveUnit bodies carry the server coordinates (e.g. 10458.40 15574.05 229.47) while the client entity is at 3290.40 4310.05 229.46; all comparisons below use the matching space.
